# 导入支付宝账单

用户上传支付宝账单（或问「这个月支付宝的钱都对上了吗」）时按这个流程走。手工记的账优先，账单用来找缺漏、核对余额，不是要把整份账单重新记一遍。

1. **找到账单**：`list_attachments` 看这次对话里的附件。没有支付宝 CSV 就先请用户上传（支付宝 App：我的 → 账单 → 右上角「…」→ 开具交易流水证明 → 交易明细，导出 CSV）。附件是 PDF 或截图时也能做，只是明细要你自己从识别出的文字里整理。

2. **看表头和期间**：`read_attachment` 读前几十行，记下三件事：表头在第几行（对账时当 `headerRow` 用）、日期范围是不是用户说的那段、有没有「收/支」「交易状态」列。列名和特殊情况见附带文件 columns.md，需要时用 `load_skill` 的 `file` 参数读：
   `load_skill(name="alipay-bill-import", file="columns.md")`。

3. **确认付款账户**：`get_accounts`。支付宝账单里的「收/付款方式」决定每笔钱从哪个账户走：余额和余额宝一般是 `Assets:` 下的支付宝账户，信用卡是 `Liabilities:` 下对应的卡，储蓄卡是 `Assets:` 下对应的银行账户。对不上号的付款方式先问用户，不要猜，也不要新建账户。

4. **对账**：`reconcile_attachment`，一次对一个付款账户：
   - `id`、`sheet`、`headerRow` 用第 2 步的；
   - `dateColumn` 填「交易时间」，`amountColumn` 填「金额」，`directionColumn` 填「收/支」（金额按账户余额变化算：支出为负、收入为正，有方向列时它说了算）；
   - `descriptionColumns` 填「交易对方」和「商品说明」，方便认出金额不一致的是哪笔；
   - `accounts` 填第 3 步确认的账户，`start`、`end` 用账单期间。
   结果里说方向可能反了，就换 `amountSign` 再对一次；多个付款方式就分几次对，别把几张卡混在一个账户里。

5. **只补账本缺的**：账本里已经有的（手工记的、之前导入的）不动。手工记录写得更清楚（分类、备注对）就保留手工的，账单里那条当已对上。同一天同一商户同金额出现两次是两笔真实消费，不要合并。

6. **写进草稿**：先 `list_files`（pattern `transactions/**/*.bean`）和 `read_file` 找到账单所在月份的流水文件；月份文件不存在就新建，并记得在入口文件 `include` 它。按日期顺序追加，`edit_file` 时把该月最后一条交易当作 old_string 的结尾，新交易接在后面。每笔：

   ```
   2026-10-05 * "瑞幸咖啡" "生椰拿铁"
     platform: "alipay"
     Expenses:Food:Coffee   18.00 CNY
     Assets:CN:Alipay       -18.00 CNY
   ```

   支出账户写正数、付款账户写负数，同一币种合计为零，金额两位小数；payee 用交易对方，narration 用商品说明；平台放 metadata，不因为平台新建账户。一笔交易一条，不要合成一条「支付宝消费」。

7. **跳过这些**：交易状态是「交易关闭」「已退款」的（退款单独记或冲销，别和原消费对消）、0 元、方向是「不计收支」的（余额宝和基金申购这类内部划转，先问用户要不要记）、花呗（除非账本里有专门的花呗账户）。

8. **校验**：`bean_check`，有错按报错改到通过。

9. **归档原件**：`archive_statement`，`provider` 填 `alipay`，`dateStart`、`dateEnd` 填账单覆盖的起止日。这样导入页的渠道覆盖和归档记录里能看到这份账单。归档也在草稿里，和交易一起写入。

10. **汇报**：对上多少笔、账单合计多少、账本合计多少、差多少；补了几笔、分别是什么；哪些没处理、为什么。差额对不上就去找真实缺漏的那笔，不要用 `Equity:Balance-Adjustments` 之类的科目把数字调平。用户要的余额校验（支付宝 App 里的余额、余额宝余额）问他要准确数字再对。
